Bloque 3 · Peldaño 3

Ese aviso que ignoramos cuatro clases

WARNING: This is a development server.
Do not use it in a production deployment.
Use a production WSGI server instead.

No es una formalidad. El servidor de flask run es un solo proceso, sin límites, sin reinicio ante fallos, pensado para que veas tu cambio al guardar.

Hoy le hacemos caso.

Bloque 3 · El contrato

WSGI: el enchufe entre el servidor y tu código

NginxHTTP → GunicornWSGI → app de Flask

Flask no sabe hablar HTTP crudo con el mundo. Sabe cumplir un contrato de Python: recibir un diccionario con la petición y devolver una respuesta.

Gunicorn es quien traduce: abre sockets, parsea HTTP, y llama a tu app como una función. Por eso podés cambiar de servidor sin tocar una línea de Flask.

Bloque 3 · Los tres roles

Quién hace qué, ahora que son tres

PostgreSQLguarda las filas
Flaskdecide qué responder — tu dominio
Gunicornejecuta Python en varios procesos, los reinicia si mueren
Nginxhabla con internet: conexiones, archivos, TLS

Cada pieza resuelve un problema distinto. Confundirlos es el origen de casi todo el dolor de despliegue.

Bloque 3 · Configuración

Cómo se levanta Gunicorn

gunicorn --workers 4 \
         --bind 0.0.0.0:8000 \
         --timeout 30 \
         --access-logfile - \
         main:app                     # módulo : objeto Flask
OpciónQué hace
--workersProcesos que atienden en paralelo. Regla inicial: 2 × núcleos + 1
--bind 0.0.0.0Escucha en todas las interfaces del contenedor, para que nginx llegue
--timeoutMata al worker que se cuelga más de 30 s y lo reemplaza
Bloque 3 · En la biblioteca

El Dockerfile cambia una línea

FROM python:3.13-slim
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN pip install uv && uv sync --frozen
COPY . .

# antes:
# CMD ["flask", "run", "--host=0.0.0.0", "--port=8000"]

CMD ["gunicorn", "--workers", "4", "--bind", "0.0.0.0:8000", "main:app"]

Nada más se mueve: ni las rutas, ni los modelos, ni las plantillas. El contrato WSGI hace que el cambio sea de una línea.

Bloque 3 · La consecuencia

Cuatro workers son cuatro memorias distintas

Cada worker es un proceso separado. No comparten variables. La petición siguiente puede caer en otro worker.

Deja de funcionar

  • Un contador en una variable global
  • Una lista en memoria como «base de datos»
  • Un archivo subido guardado en el disco del contenedor

Sigue funcionando

  • Todo lo que está en PostgreSQL
  • La sesión de Flask, firmada en una cookie
  • Lo que se recalcula en cada petición

Por eso insistimos desde la clase 3 en mover el estado a la base. Este es el momento en que esa decisión se cobra.
