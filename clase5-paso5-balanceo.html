Bloque 5 · Peldaño 5

Un contenedor sigue siendo un solo punto de falla

Gunicorn nos dio cuatro workers, pero todos dentro del mismo contenedor. Si ese contenedor se cae o hay que actualizarlo, el sitio se cae.

Nginx→ web_1 web_2 web_3

La respuesta es la misma idea de siempre, un nivel más arriba: varias copias, alguien que reparte.

Bloque 5 · Configuración

Un grupo de servidores con nombre

upstream biblioteca {
    server web_1:8000;
    server web_2:8000;
    server web_3:8000;
}

server {
    listen 443 ssl;
    location / {
        proxy_pass http://biblioteca;      # ya no un host: un grupo
    }
}

Cambió una palabra en proxy_pass. Todo lo anterior — TLS, cabeceras, estáticos — sigue igual. Así se ve una arquitectura que crece bien.

Bloque 5 · Cómo reparte

Tres formas de elegir a quién le toca

EstrategiaDirectivaCuándo
Round-robin(por defecto)Uno a cada uno, por turno. Sirve casi siempre.
Menos conexionesleast_conn;Cuando las peticiones duran muy distinto entre sí.
Por IPip_hash;Cuando el mismo cliente debe caer siempre en el mismo servidor.

Si necesitan ip_hash para que la aplicación funcione, es señal de que hay estado en la memoria del proceso. La solución de fondo no es el balanceador: es mover ese estado a PostgreSQL.

Bloque 5 · Tolerancia a fallos

Qué pasa cuando una réplica se cae

upstream biblioteca {
    least_conn;
    server web_1:8000 weight=2;                    # máquina más grande
    server web_2:8000;
    server web_3:8000 max_fails=3 fail_timeout=30s;  # 3 fallos → 30 s afuera
    server web_4:8000 backup;                       # solo si caen las demás
}

Nginx marca la réplica caída y deja de mandarle tráfico. Pasado el fail_timeout, prueba de nuevo con una petición.

El usuario no ve un error: ve la respuesta de otra réplica. Eso es alta disponibilidad, y son cuatro líneas de configuración.

Bloque 5 · En la biblioteca

Tres réplicas sin escribir tres servicios

docker compose up -d --scale web=3
upstream biblioteca {
    server web:8000;        # compose resuelve "web" a las 3 IPs
}

El DNS interno de compose devuelve las direcciones de las tres réplicas bajo el mismo nombre. Nginx reparte entre ellas sin saber cuántas hay.

Ojo: nginx resuelve el nombre al arrancar. Si escalan con nginx ya levantado, hay que recargarlo — docker compose restart nginx. En producción esto se resuelve con un resolver y variables.

Bloque 5 · La recompensa

Actualizar sin que el sitio se caiga

baja web_1→ nginx la saca→ sube nueva→ repetir con web_2

Mientras una réplica se actualiza, las otras dos atienden. El usuario no percibe nada.

Es la razón práctica por la que se replica: no es solo aguantar más carga, es poder tocar el sistema mientras está vivo.
