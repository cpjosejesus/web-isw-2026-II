Dónde quedamos

La aplicación funciona. Nadie de afuera la usa.

Lo que tenemos

  • Flask con CRUD completo sobre PostgreSQL
  • docker compose up levanta todo
  • El servidor de desarrollo escuchando en :8000

Lo que falta

  • Un solo proceso atiende una petición a la vez
  • Los archivos estáticos pasan por Python
  • Sin HTTPS, sin límites, sin réplicas

Hoy no tocamos main.py casi nada. Todo lo que agregamos vive delante de la aplicación.

La pregunta de hoy

¿Por qué poner otro servidor delante del servidor?

Suena redundante. Flask ya responde HTTP. ¿Para qué agregar una pieza más?

Flask sabe

Tu lógica: qué libro mostrar, qué guardar, qué plantilla renderizar. Eso es lo único que nadie más puede hacer por vos.

Nginx sabe

Miles de conexiones lentas, archivos, TLS, compresión, reintentos, caché. Problemas idénticos en todos los sitios del mundo.

Poner nginx delante es dejar de resolver en Python problemas que no son de tu dominio.

Ubicación

Dónde entra nginx en lo que ya conocen

4TransporteTCP — el puerto 80, el 443, el 8000

Nginx no es una capa nueva: es otro programa en la misma capa 7. Habla el mismo HTTP que Flask, hacia los dos lados.

Bloque 1 · Peldaño 1

Lo más simple que hace nginx: entregar un archivo

Navegador→ Nginx→ disco

Sin Python, sin base de datos, sin lógica. Una petición llega, nginx busca el archivo en una carpeta y lo devuelve.

Este caso ya es útil por sí solo: un sitio de HTML, CSS e imágenes no necesita nada más. Y es la base de todo lo que sigue.

Bloque 1 · Configuración

La configuración mínima, línea por línea

server {
    listen 80;                       # qué puerto atiendo
    server_name biblioteca.local;    # para qué nombre respondo

    root /var/www/biblioteca;        # dónde busco los archivos
    index index.html;                # qué devuelvo si piden "/"

    location / {
        try_files $uri $uri/ =404;   # ¿existe? sirvo. ¿no? 404
    }
}

Siete líneas. server es un sitio; location es una regla para un conjunto de URLs. Todo el resto de la clase agrega bloques dentro de esta misma forma.

Bloque 1 · El modelo mental

Una URL es una ruta de disco, hasta que deja de serlo

GET /css/estilos.css
                 │
      root /var/www/biblioteca  +  uri /css/estilos.css
                 ↓
      /var/www/biblioteca/css/estilos.css

Nginx concatena root con la URI. Si el archivo existe, lo entrega; si no, try_files decide el siguiente intento.

El error clásico: usar alias y root como si fueran sinónimos. root agrega la URI al camino; alias la reemplaza.

Bloque 1 · Por qué importa

Un proceso, diez mil conexiones

Flask en desarrollo

Un hilo atiende una petición completa. Mientras espera, no hace nada más. Cien clientes lentos = cien bloqueos.

Nginx

Un proceso maneja miles de conexiones con un bucle de eventos. Cuando una espera, atiende otra. Nadie bloquea a nadie.

Por eso el trabajo se reparte así: nginx aguanta la multitud, Flask atiende el pedido.

Bloque 2 · Peldaño 2

Un sitio no es solo archivos: entra Flask

Navegador→ Nginx→ Flask :8000→ PostgreSQL

El catálogo de libros no está en disco: se arma en cada petición. Nginx no puede generarlo, pero sabe a quién preguntarle.

Eso es un proxy inverso: nginx recibe la petición del cliente, la reenvía a otro servidor, y devuelve la respuesta como si fuera propia.

Bloque 2 · Distinción

Proxy directo e inverso: de qué lado está

Proxy directoProxy inverso
Sirve aEl clienteEl servidor
Lo configuraQuien navegaQuien publica el sitio
OcultaQuién es el clienteCómo es el backend
EjemploEl proxy de una empresanginx delante de Flask
El clienteSabe que hay un proxyNo se entera de nada

Para el navegador, nginx es el sitio. Que por detrás haya uno o veinte procesos de Flask es asunto nuestro.

Bloque 2 · Configuración

Reenviar a Flask

server {
    listen 80;
    server_name biblioteca.local;

    location /static/ {
        alias /var/www/biblioteca/static/;   # esto lo sirve nginx
        expires 30d;                         # y el navegador lo guarda
    }

    location / {
        proxy_pass http://web:8000;             # todo lo demás, a Flask
    }
}

Dos location. Nginx elige el más específico que coincida: /static/estilos.css va al disco, /libros/3 va a Flask.

Bloque 2 · La trampa

Flask deja de saber quién le habla

Con ese proxy_pass, todas las peticiones que ve Flask vienen de la IP de nginx, con el nombre de host equivocado. url_for empieza a generar enlaces rotos.

location / {
    proxy_pass http://web:8000;

    proxy_set_header Host              $host;              # el nombre real
    proxy_set_header X-Real-IP         $remote_addr;       # el cliente real
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;            # http o https
}

Estas cuatro líneas van siempre. Son la forma de decirle a la aplicación: «lo que ves viene de mí, pero el cliente original era este».

Bloque 2 · Del otro lado

Y Flask tiene que creerle

# main.py
from werkzeug.middleware.proxy_fix import ProxyFix

app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1, x_proto=1, x_host=1)

Sin esto, Flask ignora las cabeceras X-Forwarded-* — y hace bien: cualquiera puede inventarlas. ProxyFix le dice confía, pero solo en un salto.

Nunca pongan ProxyFix en una app expuesta directo a internet. Solo tiene sentido cuando hay un proxy de ustedes por delante.

Bloque 2 · En la biblioteca

Un servicio más en el compose

services:
  nginx:
    image: nginx:1.27-alpine
    ports:
      - "80:80"                                  # el único publicado ahora
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
      - ./static:/var/www/biblioteca/static:ro
    depends_on: [web]

  web:
    build: .
    expose:
      - "8000"                                   # visible en la red interna, NO afuera

ports publica al host; expose solo abre dentro de la red de compose. Flask deja de ser alcanzable desde afuera: esa es la mejora de seguridad.

Bloque 2 · Balance

Qué ganamos en este peldaño

Estáticos

El CSS ya no pasa por Python. Nginx lo lee del disco y lo cachea el navegador.

Un solo puerto

El 80 hacia afuera. La aplicación queda escondida en la red interna.

Punto de control

Un lugar donde después pondremos TLS, límites, caché y balanceo.

Pero el problema de fondo sigue: detrás de nginx todavía hay un servidor de desarrollo.

Bloque 3 · Peldaño 3

Ese aviso que ignoramos cuatro clases

WARNING: This is a development server.
Do not use it in a production deployment.
Use a production WSGI server instead.

No es una formalidad. El servidor de flask run es un solo proceso, sin límites, sin reinicio ante fallos, pensado para que veas tu cambio al guardar.

Hoy le hacemos caso.

Bloque 3 · El contrato

WSGI: el enchufe entre el servidor y tu código

NginxHTTP → GunicornWSGI → app de Flask

Flask no sabe hablar HTTP crudo con el mundo. Sabe cumplir un contrato de Python: recibir un diccionario con la petición y devolver una respuesta.

Gunicorn es quien traduce: abre sockets, parsea HTTP, y llama a tu app como una función. Por eso podés cambiar de servidor sin tocar una línea de Flask.

Bloque 3 · Los tres roles

Quién hace qué, ahora que son tres

PostgreSQLguarda las filas
Flaskdecide qué responder — tu dominio
Gunicornejecuta Python en varios procesos, los reinicia si mueren
Nginxhabla con internet: conexiones, archivos, TLS

Cada pieza resuelve un problema distinto. Confundirlos es el origen de casi todo el dolor de despliegue.

Bloque 3 · Configuración

Cómo se levanta Gunicorn

gunicorn --workers 4 \
         --bind 0.0.0.0:8000 \
         --timeout 30 \
         --access-logfile - \
         main:app                     # módulo : objeto Flask
OpciónQué hace
--workersProcesos que atienden en paralelo. Regla inicial: 2 × núcleos + 1
--bind 0.0.0.0Escucha en todas las interfaces del contenedor, para que nginx llegue
--timeoutMata al worker que se cuelga más de 30 s y lo reemplaza
Bloque 3 · En la biblioteca

El Dockerfile cambia una línea

FROM python:3.13-slim
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN pip install uv && uv sync --frozen
COPY . .

# antes:
# CMD ["flask", "run", "--host=0.0.0.0", "--port=8000"]

CMD ["gunicorn", "--workers", "4", "--bind", "0.0.0.0:8000", "main:app"]

Nada más se mueve: ni las rutas, ni los modelos, ni las plantillas. El contrato WSGI hace que el cambio sea de una línea.

Bloque 3 · La consecuencia

Cuatro workers son cuatro memorias distintas

Cada worker es un proceso separado. No comparten variables. La petición siguiente puede caer en otro worker.

Deja de funcionar

  • Un contador en una variable global
  • Una lista en memoria como «base de datos»
  • Un archivo subido guardado en el disco del contenedor

Sigue funcionando

  • Todo lo que está en PostgreSQL
  • La sesión de Flask, firmada en una cookie
  • Lo que se recalcula en cada petición

Por eso insistimos desde la clase 3 en mover el estado a la base. Este es el momento en que esa decisión se cobra.

Bloque 4 · Peldaño 4

Todo lo que enviamos viaja en texto plano

POST /libros/crear→ cualquiera en la red lo lee → título, autor, cookie de sesión

La cookie de sesión que firmamos en la clase 4 viaja en cada petición. Sin TLS, robarla es escuchar.

HTTPS es HTTP dentro de un túnel cifrado. Y ese túnel lo termina nginx, no Flask.

Bloque 4 · El modelo

Terminación TLS: el cifrado se abre en el borde

Navegador— HTTPS cifrado → Nginx— HTTP en red interna → Gunicorn

Nginx guarda el certificado y la clave privada, descifra, y reenvía en claro por una red que solo existe dentro de compose.

Ventaja concreta: el certificado se renueva y se configura en un solo lugar, aunque haya veinte réplicas de la aplicación detrás.

Bloque 4 · Configuración

Dos server: uno redirige, otro atiende

server {
    listen 80;
    server_name biblioteca.ucb.edu.bo;
    return 301 https://$host$request_uri;   # nadie se queda en http
}

server {
    listen 443 ssl;
    server_name biblioteca.ucb.edu.bo;

    ssl_certificate     /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;

    location / { proxy_pass http://web:8000; /* + las 4 cabeceras */ }
}

El 301 es permanente: el navegador lo recuerda y la próxima vez ni intenta por HTTP.

Bloque 4 · De dónde sale el certificado

Autofirmado para aprender, Let's Encrypt para publicar

En su máquina

openssl req -x509 -newkey rsa:2048 \
  -keyout privkey.pem -out fullchain.pem \
  -days 365 -nodes \
  -subj "/CN=localhost"

El navegador va a advertir. Es correcto: nadie lo avala.

En un dominio real

Certbot pide el certificado a Let's Encrypt, que verifica que el dominio es suyo sirviendo un archivo bajo /.well-known/. Gratis y automático, cada 90 días.

Un certificado no dice que el sitio sea bueno. Solo dice que el dominio es de quien dice ser.

Bloque 4 · El borde

Cosas que se resuelven una vez, para todo el sitio

add_header Strict-Transport-Security "max-age=31536000" always;
add_header X-Content-Type-Options    "nosniff" always;
add_header X-Frame-Options           "SAMEORIGIN" always;

client_max_body_size 5m;        # nadie sube un archivo de 2 GB

gzip on;                        # HTML y CSS viajan comprimidos
gzip_types text/css application/json application/javascript;

Ninguna de estas líneas es lógica de la biblioteca. Todas protegen o aceleran cualquier sitio — y por eso viven en nginx y no en main.py.

Bloque 5 · Peldaño 5

Un contenedor sigue siendo un solo punto de falla

Gunicorn nos dio cuatro workers, pero todos dentro del mismo contenedor. Si ese contenedor se cae o hay que actualizarlo, el sitio se cae.

Nginx→ web_1 web_2 web_3

La respuesta es la misma idea de siempre, un nivel más arriba: varias copias, alguien que reparte.

Bloque 5 · Configuración

Un grupo de servidores con nombre

upstream biblioteca {
    server web_1:8000;
    server web_2:8000;
    server web_3:8000;
}

server {
    listen 443 ssl;
    location / {
        proxy_pass http://biblioteca;      # ya no un host: un grupo
    }
}

Cambió una palabra en proxy_pass. Todo lo anterior — TLS, cabeceras, estáticos — sigue igual. Así se ve una arquitectura que crece bien.

Bloque 5 · Cómo reparte

Tres formas de elegir a quién le toca

EstrategiaDirectivaCuándo
Round-robin(por defecto)Uno a cada uno, por turno. Sirve casi siempre.
Menos conexionesleast_conn;Cuando las peticiones duran muy distinto entre sí.
Por IPip_hash;Cuando el mismo cliente debe caer siempre en el mismo servidor.

Si necesitan ip_hash para que la aplicación funcione, es señal de que hay estado en la memoria del proceso. La solución de fondo no es el balanceador: es mover ese estado a PostgreSQL.

Bloque 5 · Tolerancia a fallos

Qué pasa cuando una réplica se cae

upstream biblioteca {
    least_conn;
    server web_1:8000 weight=2;                    # máquina más grande
    server web_2:8000;
    server web_3:8000 max_fails=3 fail_timeout=30s;  # 3 fallos → 30 s afuera
    server web_4:8000 backup;                       # solo si caen las demás
}

Nginx marca la réplica caída y deja de mandarle tráfico. Pasado el fail_timeout, prueba de nuevo con una petición.

El usuario no ve un error: ve la respuesta de otra réplica. Eso es alta disponibilidad, y son cuatro líneas de configuración.

Bloque 5 · En la biblioteca

Tres réplicas sin escribir tres servicios

docker compose up -d --scale web=3
upstream biblioteca {
    server web:8000;        # compose resuelve "web" a las 3 IPs
}

El DNS interno de compose devuelve las direcciones de las tres réplicas bajo el mismo nombre. Nginx reparte entre ellas sin saber cuántas hay.

Ojo: nginx resuelve el nombre al arrancar. Si escalan con nginx ya levantado, hay que recargarlo — docker compose restart nginx. En producción esto se resuelve con un resolver y variables.

Bloque 5 · La recompensa

Actualizar sin que el sitio se caiga

baja web_1→ nginx la saca→ sube nueva→ repetir con web_2

Mientras una réplica se actualiza, las otras dos atienden. El usuario no percibe nada.

Es la razón práctica por la que se replica: no es solo aguantar más carga, es poder tocar el sistema mientras está vivo.

Bloque 6 · Peldaño 6

La petición más rápida es la que nunca llega a Flask

El catálogo de libros cambia pocas veces al día, pero lo recalculamos en cada visita: consulta a PostgreSQL, objetos, plantilla, HTML. Mil visitas, mil veces el mismo trabajo.

Navegador→ Nginx (¿lo tengo?)sí → respuesta guardada

Nginx puede guardar la respuesta de Flask y devolverla él mismo durante unos segundos.

Bloque 6 · Configuración

Caché de respuestas

proxy_cache_path /var/cache/nginx keys_zone=biblio:10m max_size=200m;

location /libros {
    proxy_pass http://biblioteca;

    proxy_cache biblio;
    proxy_cache_valid 200 30s;                 # 30 s de vida
    proxy_cache_methods GET HEAD;               # jamás POST
    proxy_cache_use_stale error timeout;        # si Flask cae, sirvo lo viejo

    add_header X-Cache-Status $upstream_cache_status;   # HIT / MISS
}

Esa última línea es de oro para depurar: en las DevTools ven HIT o MISS en cada respuesta.

Bloque 6 · El criterio

Qué se puede cachear y qué nunca

Sí

  • El catálogo público de libros
  • La ficha de un libro
  • CSS, imágenes, tipografías

No

  • Cualquier POST, PUT o DELETE
  • Páginas que dependen de quién está mirando
  • Todo lo que lleve datos de sesión

La pregunta es siempre la misma: ¿dos usuarios distintos verían exactamente lo mismo? Si la respuesta es no, no se cachea.

Bloque 6 · Límites

Un cliente no puede consumir todo el servidor

limit_req_zone $binary_remote_addr zone=general:10m rate=10r/s;

location /libros/crear {
    limit_req zone=general burst=20 nodelay;
    proxy_pass http://biblioteca;
}

Diez peticiones por segundo por IP, con tolerancia a ráfagas de veinte. La número veintiuno recibe 503 y nunca llega a Flask.

Defender la aplicación en el borde es más barato que defenderla adentro: el trabajo se rechaza antes de abrir una conexión a PostgreSQL.

Síntesis · Práctica

Cuando algo falla, tres comandos

docker compose exec nginx nginx -t          # ¿la sintaxis es válida?
docker compose exec nginx nginx -s reload   # recargar sin cortar conexiones
docker compose logs -f nginx                # ver qué está llegando

nginx -t siempre antes de recargar: una configuración rota deja el sitio caído. El reload levanta procesos nuevos y deja terminar a los viejos.

Para saber de quién es la culpa: si el error es 502 Bad Gateway, nginx está bien y no pudo hablar con Gunicorn. Si es 500, la excepción es de su código.

Práctica · Sobre La Carta

Lo que deben agregar a su entrega

  • Un servicio nginx en el compose; que sea el único con puerto publicado
  • /static/ servido por nginx, el resto por proxy a la aplicación
  • Gunicorn en el CMD del Dockerfile, con al menos dos workers
  • Las cuatro cabeceras de proxy y ProxyFix del lado de Flask
  • Levantar con --scale web=2 y demostrar que sigue funcionando

Se evalúa lo mismo de siempre: que docker compose up alcance, y que cada pieza esté donde le corresponde.
