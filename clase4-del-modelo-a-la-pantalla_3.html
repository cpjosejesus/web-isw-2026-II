Bloque 1 · El dominio de clase

Los dos modelos

class Autor(db.Model):
  __tablename__ = 'autores'
  id     = db.Column(db.Integer, primary_key=True)
  nombre = db.Column(db.String(120), nullable=False)

  libros = db.relationship('Libro', backref='autor',
                           lazy=True, cascade='all, delete-orphan')

class Libro(db.Model):
  __tablename__ = 'libros'
  id         = db.Column(db.Integer, primary_key=True)
  titulo     = db.Column(db.String(200), nullable=False)
  anio       = db.Column(db.Integer)
  disponible = db.Column(db.Boolean, nullable=False, default=True)
  autor_id   = db.Column(db.Integer,
      db.ForeignKey('autores.id'), nullable=False)

Bloque 2 · Plantillas

Nunca escribas una ruta a mano

<!-- ❌ frágil: si cambia la ruta, hay que buscar en 14 archivos -->
<a href="/libros/{{ l.id }}">Ver</a>

<!-- ✅ Flask construye la URL desde el nombre de la función -->
<a href="{{ url_for('detalle_libro', libro_id=l.id) }}">Ver</a>

<link rel="stylesheet"
      href="{{ url_for('static', filename='css/estilos.css') }}">

url_for recibe el nombre de la función de la vista, no la ruta. Si mañana cambias /libros/<id> por /catalogo/<id>, no tocas ni una plantilla.

Bloque 2 · Plantillas · seguridad

Jinja te está protegiendo

# un usuario guarda este título de libro:
titulo = '<script>robarSesion()</script>'

# Jinja lo imprime escapado, como texto inofensivo:
&lt;script&gt;robarSesion()&lt;/script&gt;

El filtro |safe desactiva esa protección y vuelve a habilitar XSS. Úsalo solo sobre HTML que generaste tú, nunca sobre algo que escribió un usuario.

Mismo principio que el %s de psycopg2: el peligro aparece cuando mezclas datos del usuario con código.

Bloque 4 · CRUD

CREATE — la ruta completa

@app.route('/libros/crear', methods=['GET', 'POST'])
def crear_libro():
  if request.method == 'GET':
    return render_template('libros/formulario.html',
                           autores=Autor.query.all())
  try:
    l = Libro(
      titulo=request.form['titulo'],
      anio=request.form.get('anio') or None,
      autor_id=request.form['autor_id']
    )
    db.session.add(l)
    db.session.commit()
    flash('Libro creado.', 'exito')
  except Exception:
    db.session.rollback()                # la transacción de la clase pasada
    flash('No se pudo crear.', 'error')
  finally:
    db.session.close()

  return redirect(url_for('listar_libros'))
Bloque 4 · CRUD

POST → Redirect → GET

POST /libros/crear→ 302 Redirect→ GET /libros

Si respondes al POST con render_template, el navegador se queda "parado" sobre el POST. El usuario presiona F5… y crea el mismo libro otra vez.

Con el redirect, la última petición del historial es un GET inofensivo. Recargar solo vuelve a listar.

Este patrón tiene nombre propio: Post/Redirect/Get. Es de los pocos que hay que aplicar siempre, sin pensarlo.

Bloque 4 · CRUD

READ — listado y detalle

@app.route('/libros')
def listar_libros():
  autor = request.args.get('autor')              # ?autor=Kurose
  consulta = Libro.query
  if autor:
    consulta = consulta.join(Autor).filter(Autor.nombre.ilike(f'%{autor}%'))
  return render_template('libros/index.html',
                         libros=consulta.order_by(Libro.titulo).all())

@app.route('/libros/<int:libro_id>')
def detalle_libro(libro_id):
  l = Libro.query.get_or_404(libro_id)
  return render_template('libros/detalle.html', libro=l)

get_or_404 reemplaza el if ... is None: abort(404) de la clase pasada. Y <int:libro_id>, que ya conocen, rechaza /libros/abc antes de tocar la base.

Bloque 4 · CRUD

UPDATE — el objeto ya está vigilado

@app.route('/libros/<int:libro_id>/editar', methods=['GET', 'POST'])
def editar_libro(libro_id):
  l = Libro.query.get_or_404(libro_id)

  if request.method == 'GET':
    return render_template('libros/formulario.html', libro=l,
                           autores=Autor.query.all())

  l.titulo = request.form['titulo']      # solo asignas atributos
  l.anio   = request.form.get('anio') or None
  db.session.commit()                     # el ORM genera el UPDATE

  return redirect(url_for('detalle_libro', libro_id=l.id))

No hay db.session.add(): el objeto vino de una consulta, así que la sesión ya lo está vigilando y detecta el cambio sola.

Bloque 4 · Errores

Que el error también sea tuyo

@app.errorhandler(404)
def no_encontrado(error):
  return render_template('errores/404.html'), 404

@app.errorhandler(500)
def error_servidor(error):
  db.session.rollback()          # deja la sesión limpia
  return render_template('errores/500.html'), 500

Fíjense en el segundo valor de retorno: es el código de estado. Sin él responderías 200 OK con una página que dice "no encontrado" — mentirle al navegador y a los buscadores.

Bloque 4 · Rendimiento

El SQL que no ves: N+1

{% for l in libros %}
  {{ l.titulo }} — {{ l.autor.nombre }}      ← una consulta por cada libro
{% endfor %}

Con 50 libros: 1 consulta + 50 consultas. La página funciona, se ve bien… y tarda dos segundos.

# una sola consulta, con JOIN
Libro.query.options(db.joinedload(Libro.autor)).all()

Enciendan SQLALCHEMY_ECHO = True y cuenten las líneas al cargar el listado. Es la demostración más contundente de por qué hay que saber qué SQL genera el ORM.

Síntesis

Checklist de una ruta bien escrita

  • ¿El verbo corresponde? Lectura → GET, escritura → POST.
  • ¿Los datos se leen de request.form o request.args, según el verbo?
  • ¿Hay try / except / rollback / finally alrededor del commit?
  • ¿Termina en redirect si modificó algo?
  • ¿Usa url_for en vez de rutas escritas a mano?
  • ¿Devuelve el código de estado correcto?

Bloque 5 · Cómo se evalúa

Lo que voy a mirar

  • Herencia de plantillas: un solo layout.html; ninguna plantilla repite el <head>.
  • Cero rutas escritas a mano: todo enlace y todo action pasa por url_for.

Bloque 5 · Entrega

Dentro del contenedor, localhost es otro

postgresql://lacarta:clave@db:5432/lacarta
                           └┬┘ └─┬┘
                    nombre del  puerto
                     servicio

Cada contenedor tiene su propia interfaz de red. Dentro de web, localhost es el propio contenedor web, donde no hay ninguna base de datos.

Compose crea una red interna donde el nombre del servicio es el nombre de host. Sigue siendo dirección + puerto: solo cambia cómo se resuelve la dirección.
